
# 「公開してみよう。」せっかく作ったなら、GitHubで公開してみる

🔗 公開Webツール（GitHub Pages）：
https://tk030-lotto.github.io/kokai-shitemiyou-tool/

AIを使ってソフトウェアを作った。

動いた。

自分でも使える。

ここまではできた。

でも、その次に、

> **「これ、どうやって人に見せればいいんだ？」**

となることがあります。

AIに作ってもらうところまではできても、GitHubに公開するところで止まってしまう。

そんな人向けに、今回、小さなWebツールを作りました。

その名前は、

# 「公開してみよう。」

です。

---

## 作ったものを、自分だけで終わらせない

AIを使えば、以前より簡単にソフトウェアを作れるようになりました。

小さなWebアプリ。

ファイル名変更ツール。

CSV集計ツール。

自分用の業務ツール。

ちょっとした便利ツール。

自分で使うだけなら、そこで完成です。

でも、

> **「せっかく作ったんだから、誰かにも見てもらおう」**

と思うことがあります。

ところが、そこでGitHubが出てくる。

GitHubアカウントを作る。

リポジトリを作る。

ファイルを登録する。

READMEを書く。

ライセンスを考える。

GitHub Pagesを設定する。

……。

急に難しそうに見えてきます。

そこで、

**公開するところまでの手順を、順番に案内するだけのツール**

を作りました。

---

# 「公開してみよう。」のコンセプト

このツールの目的は、GitやGitHubを詳しく教えることではありません。

もっと単純です。

> **「GitHubって難しそう」**

という状態から、

> **「自分の作ったものを公開できた」**

という状態へ進むこと。

これが目的です。

そのため、難しい専門知識を最初から覚える必要はありません。

必要なところを、その都度確認しながら進めていきます。

---

# まず「何を公開するのか」から

最初に、

**「何を公開しますか？」**

と聞きます。

例えば、

> ファイル名変更ツール

> CSV集計ツール

> HTMLで作ったWebアプリ

> Pythonツール

> 小さな業務ツール

など。

難しい説明は必要ありません。

---

# 公開前に確認する

いきなりGitHubへアップロードするのではありません。

まず、

**公開して大丈夫なのか？**

を確認します。

例えば、

* 実際に動作するか
* 必要なファイルが揃っているか
* 不要なファイルが入っていないか
* READMEがあるか
* 使い方が説明されているか
* ライセンスが必要か

などです。

そして、もう一つ重要なのが、

**公開してはいけない情報が入っていないか**

です。

例えば、

* APIキー
* パスワード
* アクセストークン
* 個人情報
* 非公開情報
* ローカル環境固有の情報

など。

こういうものをうっかりGitHubに公開してしまうと困ります。

だから、公開前に一度確認します。

---

# GitHubを準備する

GitHubアカウントを持っていなければ、アカウント作成から案内します。

すでに持っていれば、そのまま次へ進めます。

そして、新しいリポジトリを作ります。

ここでは、

* リポジトリ名
* 説明
* Public / Private
* README
* ライセンス

などを確認します。

---

# Gitコマンドは必須にしませんでした

ここは今回、かなり意識したところです。

GitHubを使うとなると、

> 「Gitを覚えないといけないの？」

と思う人もいると思います。

でも今回のツールでは、初期版では、

**Gitコマンドを使わず、GitHubのWeb画面からファイルを登録する方法**

を基本にしています。

もちろんGitを使える人は使えばいい。

でも、

**Gitを知らないから公開できない**

という状態にはしたくありませんでした。

---

# READMEも大事

GitHubに公開するなら、READMEがあったほうがいい。

最低限、

* プロジェクト名
* 何をするものなのか
* 使い方
* 必要な環境
* ライセンス

などを書いておく。

でも、

> 「READMEなんて書けない」

となるかもしれません。

そこで、これもAIに作ってもらえばいい。

このツールでは、READMEについてもAIに作成してもらう方法を案内します。

---

# ライセンスも難しく考えすぎない

OSSとして公開するなら、ライセンスについて考える必要があります。

ただ、今回のツールでは特定のライセンスを無理に押し付ける設計にはしていません。

分からなければ、

**AIに聞く。**

公式情報を確認する。

そして、自分で決める。

という形です。

---

# WebアプリならGitHub Pages

今回のツール自身もWebアプリなので、GitHub Pagesで公開することを想定しています。

基本的な流れは、

1. GitHubリポジトリを作る
2. HTML / CSS / JavaScriptなどを登録する
3. GitHub Pagesを有効にする
4. 公開URLを確認する
5. ブラウザで動作確認する

です。

これも順番に案内します。

---

# 公開したら終わりではない

ここも大事です。

GitHub PagesのURLが表示された。

だから終わり。

ではありません。

実際に公開されたページを開いて、

* ページが表示されるか
* リンクが動くか
* JavaScriptが動くか
* 画像が表示されるか
* READMEが正しく表示されるか

を確認します。

自分のPCでは動いていたのに、公開したら動かない。

こういうこともあります。

だから最後に、**公開された状態で実際に確認する**。

ここまでをガイドに入れています。

---

# そして、困ったらAIに聞けばいい

公開途中で、

> 「ここが分からない」

となることもあります。

そこで、このツールでは問題が発生した場合に、姉妹ツールの、

**「AIに聞いてみよう。」**

や、

**「エラーで止まらない。」**

へ誘導する構成にしています。

つまり、

**公開する → 分からない → AIに聞く → また進む**

という流れです。

---

# 自動公開にはしませんでした

「じゃあ、GitHub APIと接続して全部自動化すればいいのでは？」

と思うかもしれません。

確かにできます。

でも、今回はやりませんでした。

このツール自身は、

* GitHub API連携
* Git操作
* 自動リポジトリ作成
* 自動ファイルアップロード
* 自動デプロイ
* 自動GitHub Pages設定
* 自動公開

を行いません。

GitHubアカウントへ直接アクセスすることもありません。

ログイン情報やアクセストークンを取得することもありません。

---

# なぜ自動化しなかったのか

理由はシンプルです。

今回作りたかったのは、

**「公開を自動化するツール」ではなく、「公開できるようになるための案内役」**

だからです。

自分でGitHubを操作する。

自分で公開ボタンを押す。

自分で公開されたものを確認する。

この経験を一度しておけば、次からは少し楽になります。

---

# 「公開する」こと自体が経験になる

最初は、

> 「GitHubって難しそう」

と思うかもしれません。

でも、一度やってみると、

「ああ、こういうことか」

となる。

リポジトリを作る。

ファイルを登録する。

READMEを書く。

ライセンスを設定する。

GitHub Pagesを設定する。

URLを開く。

たった一度でも、この流れを経験することには意味があると思っています。

---

# 完璧じゃなくても公開していい

もう一つ、このツールで伝えたいことがあります。

> **「まだ完璧じゃないから公開できない」**

と考えなくてもいい。

もちろん、公開してはいけない情報が入っていないかなど、最低限の確認は必要です。

でも、

**小さなツールなら、まず公開して、あとから直す**

というやり方もあります。

READMEに、

> 現在開発中です

と書いてもいい。

バージョンアップしてもいい。

バグを直してもいい。

改善してもいい。

公開したから完成、ではありません。

---

# 今回も、作って終わりにはしませんでした

今回の「公開してみよう。」も、小さなWebアプリとして作りました。

Step 0〜8のステップ形式で、

**入力 → 公開前チェック → GitHub準備 → リポジトリ作成 → ファイル登録 → README・ライセンス → GitHub Pages → 公開後確認**

までを案内する構成です。

ブラウザサブエージェントを使って全ステップを検証し、エラー0件で動作確認も行いました。

さらに、5段階の品質監査では、

**100 / 100点、PASS**

となっています。

全11ファイルが300行未満で、最大285行。

Zero-Dependency。

UI/UX、セキュリティ・プライバシー、Git・ドキュメント整合性まで確認しています。

小さなツールだからこそ、最後まで確認してから公開する。

これは今回も同じです。

---

# AIで作ったものを、AIだけの中に置いておかない

AIを使えば、ソフトウェアを作れる。

でも、

AIで作ったものを自分のPCの中だけに置いておく必要もありません。

小さなツールでもいい。

自分しか使わないものでもいい。

試作品でもいい。

公開してみる。

誰かが使うかもしれない。

誰かが感想をくれるかもしれない。

バグを見つけてくれるかもしれない。

そこから改善できるかもしれない。

そして、

**次に作るものが見えてくるかもしれない。**

READMEにも、この考え方を「まず公開してみる」というコンセプトとして整理しています。

---

# 「公開してみよう。」を作った理由

AI開発を始める。

↓

何か作ってみる。

↓

動いた。

↓

自分でも使える。

↓

でも、GitHubに公開する方法が分からない。

ここで止まってしまう。

それは少しもったいない。

だから、

> **「公開してみよう。」**

という小さな案内役を作りました。

GitHubの専門家になるためのツールではありません。

Gitを極めるためのツールでもありません。

ただ、

**「自分で作ったものを、一度公開してみる」**

その最初の一歩を手伝うだけです。

---

# おわりに

AIを使ってソフトウェアを作ることが、以前より身近になりました。

だからこそ、

**作った後に何をするか**

も大事になってくると思います。

作った。

動いた。

それで終わりでもいい。

でも、もし、

> 「せっかく作ったなら、誰かにも見てもらいたい」

と思ったら、

一度公開してみる。

完璧じゃなくてもいい。

小さくてもいい。

分からなければAIに聞けばいい。

そして、公開してみる。

その一歩を踏み出すためのツールとして、

**「公開してみよう。」**

を作りました。
